# Project Context: Apeira

## 1. Executive Summary & Vision
**Apeira** is a modular, high-performance Minecraft Java mod built on **NeoForge 26.3** (Java 25). 

The goal of Apeira is to bring the rich, custom, interactive survival server experience of *Origin Realms* into a **native, singleplayer/multiplayer modded environment**.

### Why Apeira Exists:
* **Eliminate Server-Side Hackiness & Entity Lag:** Traditional custom servers rely heavily on display entities, invisible armor stands, complex resource pack hacks, and plugin overhead. This creates massive server TPS drop, entity tick lag, and rendering stutters.
* **Native Modded Performance:** Apeira replaces command blocks, plugins, and armor-stand tricks with clean, data-driven NeoForge blocks, VoxelShapes, custom client-side block entity renderers, and payload-driven UI networks.
* **Modular Architecture:** Rather than building a single monolithic mod file, Apeira is split into **three foundational library subprojects** (`apeira-core`, `apeira-decor`, `apeira-story`), **one main content module** (`apeira-main`), **one archaeology content module** (`apeira-archae`) **one dev-only tools module** (`apeira-dev`) and **one client-only UI capture tool** (`apeira-uicapture`).

---

## 2. Technical Stack & Foundation
* **Target Engine:** Minecraft Java Edition / **NeoForge 26.3**
* **Language / JDK:** Java 25 (Minecraft 26.x requires it)
* **Build System:** Gradle Multi-Project using the official `net.neoforged.moddev` plugin
* **Asset Pipeline:** Data Generators (Datagens) + Python scripts in `scripts/` for model, texture and hitbox conversion (see section 6)
* **Rendering & Animation:** Fast TileRenderers, standard VoxelShapes, custom block entities, GeckoLib for complex mobs/bosses

4. Feature Roadmap & Execution Tree
Development follows a strict Dependency Tree to prevent feature bloat and burnout:

Phase 1: Foundation & Pipeline → Registries, Datagens, and Python automation. (Done)

Phase 2: Core Content → Blocks, items, foods (food data components), shaped/shapeless recipes. (In progress: every block and item of the legacy ORForged mod ported, with its textures or, where it had none, the Origin Realms server pack's, see section 7)

Phase 3: Furniture & Seating → Directional VoxelShapes, Mount Entities, network payloads. (In progress: 198 legacy furniture pieces ported, 15 of them seats, see section 8)

Phase 4: Painting System → Canvas block entity, color palettes, custom dynamic textures. (In progress: painting table, paintbrush, paintable furniture and finish shaders ported from CosmoLib, see section 9)

Phase 5: Cosmetics & Crates → Player model layers, Crate block entity, client-side roll animations. (In progress: CosmoLib's cosmetics, wardrobe and crates and the Crates mod's cosmetics, furniture and 15 crates ported, see sections 8, 10 and 11)

Phase 6: Biomes & Worldgen → 26.3 surface rules, custom wood types, custom dimension. (In progress: Xenon's worldgen, biomes, trees, ores and spawns ported, see `MainWorldgen` in section 7; ORForged's other woods have no saplings or trees yet)

Phase 7: Mobs, NPCs & Quests → GeckoLib entities, pathfinding AI, dialogue UI, quest journal.

Phase 8: Bosses & Specials → Multi-phase boss state machines, special abilities, arena triggers.

5. Coding Standards & AI Directives (FOR CLAUDE CODE)
CRITICAL INSTRUCTIONS FOR CLAUDE CODE:

Modern Registry Patterns Only: Always use DeferredRegister, DeferredItem, and DeferredBlock. Never call legacy Forge Registries or direct constructors.

Identifier Standard: Minecraft 26.x renamed ResourceLocation to net.minecraft.resources.Identifier. Always use ApeiraIds.id("path") or Identifier.fromNamespaceAndPath("apeira", "path"). NEVER instantiate new Identifier(...) or refer to ResourceLocation.

Data-Driven over Hardcoded Java: Furnace fuel and composter chances are item properties in 26.x (Item.Properties#cookingFuel and #compostable, keyed into the minecraft:context_int_provider registry); NeoForge 26.3 removed its furnace_fuels and compostables data maps. Food values are the food data component (Item.Properties#food). Custom per-item values (sell prices, quest rewards) use data maps under data/<namespace>/data_maps/..., written with ApeiraDataMapProvider.

Networking: Use modern CustomPacketPayload and PayloadRegistrar. Never use obsolete byte-buffer packet channels.

Emissive Texels (alpha 254): a texel with alpha exactly 254 (`0xFE`) is fullbright and opaque, alpha 255 is opaque and lower alphas blend. Paint glowing parts (flames, lamps, runes) with alpha 254 instead of adding a glow texture. GeckoLib renderers draw with `EmissiveRenderTypes#entityTranslucent` (or `entityTranslucentCull`), never vanilla's `RenderTypes.entityTranslucent`, and new item or furniture shaders must keep `apeira:emissive.glsl`'s check (section 9).

No Entity-Lag Hacks: Do not use invisible armor stands or display entities for seating or furniture. Use VoxelShapes, BlockEntities, or temporary non-ticking mount entities.

Code Quarantine: Legacy code in /reference_code/ is strictly READ-ONLY. Use it to extract mathematical formulas, custom algorithms, and asset references, but completely rewrite registration and network logic for NeoForge 26.3.

Strict Library Separation: Generic utilities MUST go into apeira-core, apeira-decor, or apeira-story. Do not contaminate apeira-main with underlying framework code.

6. Asset Automation Scripts (`scripts/`)
Python 3.10+ scripts that use only the standard library. Run them from the repository root; each has `--help`, and every default path below can be changed with an option. Scripts that write files never replace an existing file unless given `--force`, and accept `--dry-run` to only print what they would do. Tests: `python -m unittest discover -s scripts/tests`.

process_server_pack.py: Converts the custom models of the Origin Realms server pack (default `reference_code/server_resource_pack/`, which is git-ignored) into `apeira-main/src/main/resources/assets/apeira/models/item/<name>.json`. It reads both CustomModelData formats: legacy `overrides` in `assets/minecraft/models/item/*.json`, and the 1.21.4+ item definitions in `assets/minecraft/items/*.json` that the current pack actually uses (`range_dispatch`, `select` or `condition` on `custom_model_data`). Models are named after their file in snake_case, with parent folder names added only where two would clash; pack parent models are copied too, and texture references move to `apeira:item/...` or `apeira:block/...`. `--copy-textures` copies the textures, `--item-definitions` also writes `assets/apeira/items/<name>.json` (only needed for items whose definition is more than one model, such as bows or trimmed armour, since datagen writes plain ones), `--base-item` and `--match` pick a subset, and a CustomModelData -> item report goes to `build/asset-scripts/server_pack_manifest.json`.

flatten_textures.py: Moves every texture under `assets/apeira/textures/` up to its first folder (`item/`, `block/`, ...; the atlases load sprites by those folders, so they stay) and renames files to lowercase snake_case, carrying `.png.mcmeta` files along and updating texture references in `assets/apeira/models/`. Two files that would get the same name are reported and left in place (exit code 1), or with `--on-collision prefix` get their parent folder names as a prefix.

make_placeholder_textures.py: Draws a 16x16 placeholder PNG into `apeira-main/src/main/resources/assets/apeira/textures/` for every `apeira:block/...` or `apeira:item/...` texture that a generated model refers to but that does not exist yet: bricks for blocks, a gem shape for items, coloured from the texture name. Run it after datagen adds a block or item; real textures replace the placeholders, which are never overwritten without `--force`.

parse_blockbench_hitboxes.py: Reads `.bbmodel` or Java model JSON files and prints `VoxelShape` constants built from `Block.box(x1, y1, z1, x2, y2, z2)` in pixel coordinates, for apeira-decor furniture. Flat cubes are dropped, contained cubes removed and aligned cubes merged; rotated cubes use the box around their corners. A Blockbench outliner group named `hitbox` or `collision` is used on its own when present. `--facings` adds east, south and west versions of a north-facing model, `--bounds` gives one box, `--min-size` drops small details, `--clamp` cuts boxes to the block, and `-o` writes to a file.

7. Content Layout (`apeira-main`)
Content lives in holder classes under `com.apeira.main.registry`, each with a static `init(ApeiraRegistrar)` that `Apeira`'s constructor passes to `REGISTRAR.register(...)` as a `RegistryModule`. Data providers live under `com.apeira.main.datagen` and are added in `MainData.init`, which `Apeira` passes to `DATA.register(...)`.

Legacy source: the content is the legacy ORForged mod's (`Meh-19/orforged-1.20.1-0.1`, which has the textures and lang; `orforged-1.20.4` has the same registries). Names, ids, textures and properties are ORForged's. ORForged had no recipes beyond fungal, vertical planks and beams, so the others follow vanilla (see `MainRecipeProvider`). Every block ORForged registers is ported. 91 of them had no texture in ORForged (stone variants, stained stone, lanterns, mineral bricks and pillars, vanilla vertical planks); their textures and models are the Origin Realms server pack's (`assets/originrealms/{textures,models}/block/misc_blocks/{earth,stone,lanterns}/` and `.../minerals/`), from the extracted pack on Ren's computer. ORForged has no vines or lily pads, and no block of it ticks.

MainItems: `platinum` and `ruby`; platinum's sword, pickaxe, axe, shovel and hoe (`PLATINUM_TOOL_MATERIAL`: diamond tier, 500 uses, speed 7, +2.2 damage, enchantability 12, repaired with `#apeira:platinum_tool_materials`; every tool gets 3 attack damage and attack speed 2, as in ORForged) and armour (`PLATINUM_ARMOR_MATERIAL`: durability 25, defence 2/6/7/3, enchantability 12, iron's equip sound, `#apeira:repairs_platinum_armor`). The armour model is the hand-made equipment asset `assets/apeira/equipment/platinum.json` (`textures/entity/equipment/humanoid{,_leggings}/platinum.png`, ORForged's armour layers; no baby layer). Armour items use NeoForge's dynamic trim model (`ApeiraItemModelProvider#trimmableArmor`), so trims show without a model per trim material.

MainBlocks: platinum and ruby blocks, bricks and pillars (an iron block's properties, strength 5/6, stone sounds; pillars are `RotatedPillarBlock`s), their ores and deepslate ores (`DropExperienceBlock`, 2-5 experience, stone with hardness 2; ores need a stone tool, deepslate ores iron, and drop the material with Fortune or themselves with Silk Touch), and bricks and pillars of diamond, emerald, gold, iron and netherite (`MainBlocks#vanillaMinerals`, each copying its vanilla block; four bricks from four blocks, two pillars from two). All are mined with a pickaxe.

MainStones: ORForged's 43 stone variants ("Earth": andesite, diorite, granite, stone, dripstone, mud, slate, limestone, packed dirt and sands, silt, blue, tainted and red nether bricks, soul and basalt bricks) and 9 `stained_stone_<light|dark>_<n>` shades, plain blocks copying the vanilla block ORForged copied. Chiseled blocks and slate (`MainStones#columns`) have a `block/<name>_top` end texture. Pickaxe, except packed dirt, packed sands and silt (`MainStones#soils`, shovel); ORForged's `needs_stone_tool` list is kept. Recipes: each is cut in a stonecutter from its base block (crafting four would clash with vanilla's polished stones and sandstone), dried silt is smelted silt, blue nether bricks are red nether bricks' recipe with warped fungus; slate, limestone and silt are natural and have none. Names are the ids in title case (ORForged called every stained stone "Stone").

MainLanterns: 19 lanterns (paper lanterns for the eight vanilla woods, bamboo, fungal and ORForged's seven woods; crimson and warped shroom lanterns), glowstone's properties with light 15, strength 2/3 and scaffolding sounds, `block/<name>` sides and `block/<name>_top` ends, axe. Recipe: paper on the four sides of a torch with the wood's planks in the corners.

Biomes: maple forest, foothills, cold maple forest, cold birch forest and The Depths, placed without TerraBlender by `MainBiomePlacement` (`mixin/OverworldBiomesMixin` lists them at unreachable climate points; `mixin/MultiNoiseBiomeSourceMixin` wraps the source's resolver): below y -48 and in place of the deep dark it is The Depths; above, ~512-block regions with TerraBlender's weights (vanilla 10, Xenon's four 4 each) turn forest, windswept hills, taiga, old growth pine taiga and old growth birch forest into Xenon's biomes, keeping vanilla terrain. They are not in `#minecraft:is_overworld`, as in Xenon. `data/minecraft/dimension_type/overworld.json` (Xenon's override) lowers the overworld to y -128 (height 448); `DepthsTerrain` (`mixin/DepthsTerrainMixin`, after `NoiseBasedChunkGenerator#buildSurface`, only in dimensions reaching y -128) fills -128 to -64 and carves Xenon's caverns, shafts, crystals and hangs. `ambient.depths` is The Depths' loop.

MainWoods: seven trees (maple, bleak, fir, palm, bayou, wisteria, baobab), each with a log, wood, stripped log and wood (strength 4), planks with stairs, slab, button, pressure plate, fence and gate (core's `PlankSet`), vertical planks, carved planks (`<wood>_planks_carved`), one or two leaves colours and a beam; plus `palm_crown`, four `wisteria_flowers_<colour>`, `fungal` planks in plain and 16 dyed sets with vertical and carved fungal planks, beams and carved planks for the ten vanilla woods, and vertical planks for those and bamboo (`MainWoods.VANILLA_VERTICAL_PLANKS`: the server pack draws them with the vanilla planks texture turned on its side, through the hand-made parent model `models/block/vertical_planks.json`). Leaves are vanilla `LeavesBlock`s, which decay by their `distance` state; maple and fir leaves drop their sapling (Xenon's flat 5%, `maple_sapling`/`fir_sapling`, a `TreeGrower` with Xenon's `maple_tree`/`fir_tree`), the others, with no saplings, drop sticks, or themselves with shears or Silk Touch (`ApeiraBlockLootProvider#createLeavesDropsWithoutSapling`). Axe stripping is the `neoforge:transformables` data map and burning the `neoforge:flammable` data map (`MainDataMapProvider`, vanilla's odds); wooden items burn in furnaces through `cookingFuel`. Each tree's logs are in `#apeira:<wood>_logs` (`MainTags#logs`), which is in `#minecraft:logs_that_burn`; planks, leaves and shapes are in vanilla's block and item tags (`MainBlockItemTags`, written by both tag providers). `MainWoods#all` lists every block it registers.

MainCreativeTabs: the `Apeira Content` tab (`apeira:content`, title key `itemGroup.apeira.content`, ruby icon), registered with `ApeiraRegistrar#creativeTab`. It lists every item of the registrar's item register in registration order, so new blocks and items appear in it without changes here, except cosmetics and crates, which are in the `Cosmetics` tab (`apeira:cosmetics`, western hat icon): crates first, then cosmetics grouped by crate.

MainCosmetics and MainCrates: the Crates mod's cosmetics and crates, see sections 10 and 11.

Datagen: `MainBlockStateProvider` (block states and models: cubes with a `block/<name>` texture; pillars, logs and beams with `block/<name>` sides and `block/<name>_top` ends and a horizontal model; woods with their log's side texture; wood families through vanilla's `BlockModelGenerators#family`), `MainModelProvider` (flat and handheld item models, `item/<name>` texture), `MainRecipeProvider` (shaped, shapeless, smelting and blasting recipes; wood families through vanilla's `RecipeProvider#generateRecipes`), `MainBlockLootSubProvider` (block loot tables), `MainBlockTagProvider` and `MainItemTagProvider` (tool, armour, wood and mining tags), `MainDataMapProvider` (stripping and flammability) and `MainLanguageProvider` (en_us names and the tab titles). Core helpers for these: `ApeiraRegistrar#blockWithItem(name, factory, Supplier<Properties>, itemProperties)` (copied properties and fuel items), `PlankSet`, `ShapeSet` (stairs, slab and wall of a block), `ApeiraBlockStateProvider#log/family/pillar/leaves/shapes`, `ApeiraBlockLootProvider#dropShapes`, `ApeiraItemTagsProvider` (`ApeiraDataGenerators#itemTags`), `BlockAndItemTags` for tags written to both registries, and `ApeiraDataMapProvider#strippable/flammable`. Loot tables are datapack registry entries in 26.x like recipes: core's `ApeiraBlockLootProvider` extends vanilla's `BlockLootSubProvider`, `ApeiraDataGenerators#blockLoot` runs it through `GatherDataRegistryEntriesEvent`, and it only checks the registrar's own blocks, so every new block needs a loot table (or `noDrop()`) or the data run fails. Block tags extend core's `ApeiraBlockTagsProvider` (NeoForge's `BlockTagsProvider`) and are added with `ApeiraDataGenerators#blockTags`; in 26.x tag appenders take `ResourceKey`s, which its `add(tag, blocks...)` helper takes from each `DeferredBlock`. Core's `ApeiraModelProvider` is final and runs every model provider of a module, so module model providers extend `ApeiraBlockStateProvider` or `ApeiraItemModelProvider`. Register client-only providers (block states, item models) in `MainData` with lambdas, not constructor references, so a dedicated server never loads their classes.

Generated resources: `./gradlew :apeira-main:runData` writes to `apeira-main/src/generated/resources/`, which is committed. CI runs it and fails when the committed files are out of date. The other modules' data runs are apeira-main's too: `runDecorData` (section 8) and `runArchaeData` (section 12); CI runs all three and checks each module's `src/generated`. The language file is generated, so `assets/apeira/lang/en_us.json` must not also exist in `src/main/resources`.

Textures: `src/main/resources/assets/apeira/textures/{block,item}/<name>.png`, ORForged's (or the server pack's, for the blocks above that ORForged had none for, renamed `<name>` and `<name>_top`), copied as they are except `<x>_pillar_side` (now `<x>_pillar`) and `<wood>_planks_carved_top` (now `<wood>_planks_carved`, used on every side, the only carved texture ORForged has). The ores and the crimson and warped beams are animated (`.png.mcmeta`).

Creative tab: the `Apeira Content` tab also lists the decor module's items (furniture, painting table, paintbrush), after the main module's.

8. Furniture & Seating (`apeira-decor`)
apeira-decor depends on apeira-core and has its own `ApeiraRegistrar` (`ApeiraDecor.REGISTRAR`, shared `apeira` namespace; entity types use `ApeiraRegistrar#entityType`) and `ApeiraDataGenerators` (`ApeiraDecor.DATA`). Holder classes are under `com.apeira.decor.registry`, data providers under `com.apeira.decor.datagen` (added in `DecorData.init`).

Blocks (`com.apeira.decor.block`): `ApeiraFurnitureBlock` is the abstract base, CosmoLib's furniture system (see "CosmoLib unification" below): a `PaintableBlock` with `ROTATION` 0-7 (eight 45 degree turns, `yaw(rotation)` = rotation x 45, as `Direction#toYRot` measures it) that faces the placing player, renders `INVISIBLE` (a block entity renderer draws its item) and takes its shape facing north, turned for each rotation (the box around each turned box at the diagonals). Sitters face out of the front (`SeatBlock#seatYaw`). Shapes and models are authored facing north (the front, where a sitter looks out, on the north side); build the shape with `parse_blockbench_hitboxes.py` from the model. `SeatBlock` is any block with a seat (`seatHeight()`, in blocks); `SeatBlock#use` does the right-click sitting, and sneaking players and players already riding don't sit. `ApeiraChairBlock` is a furniture base with a seat height in pixels. Minecraft 26.x blocks have no codecs, so subclasses only need a `(Properties)` constructor. Furniture blocks need `noOcclusion()`.

Seating (`com.apeira.decor.entity`): `ApeiraSeatEntity` (`apeira:seat`, `DecorEntities.SEAT`) is an invisible, zero-size entity spawned at the chair centre at seat height, so its block position is the chair's. One seat per chair: sitting reuses an empty seat and fails if someone already sits there. Its tick does nothing but discard it when it has no passenger or its block is no longer a chair, and it discards itself when its passenger dismounts; riding is forced, so the dismount cooldown does not block getting back up. Players stand up in front of the chair (else beside, behind, then on top). It is saved with the chunk because vanilla only lets players ride savable entities, which also reseats a player who logged out sitting. Every entity type needs a client renderer even when invisible: `client/ApeiraDecorClient` (`@Mod(dist = Dist.CLIENT)`) registers a `NoopRenderer`.

Furniture (`com.apeira.decor.furniture`, registered by `registry/DecorFurniture`): 198 pieces, each a `FurnitureBlock` (a `FurnitureBlock.Seat`, which is a `SeatBlock`, when it has a seat) with a block item of the same name. They are listed in `FurnitureCatalogue`, a data table generated once from the legacy models and edited by hand from now on. Each entry is a `Furniture`: id, crate, paintability, default paint, collision, seat height, large-piece rendering and shape (pixels, facing north). Datagen loops over `DecorFurniture.all()`. Properties are the Crates mod's: strength 1, wood sound, no occlusion. Every piece is mined with an axe (`minecraft:mineable/axe`) and drops itself, keeping its paint. Crate pieces name their crate in gold through the `minecraft:lore` component (`tooltip.apeira.exclusive.<crate>`, also written by the decor language provider). The pieces are:
- 195 of the Crates mod's 296 (`Meh-19/Crates-NeoForge-1.21.1`, `CratesBlocks`, `models/furniture/<crate>/<name>.json`).
- ORFurniture's two unregistered models: `sofa_chair` (its `chair` model) and `iron_table`.
- CosmoLib's `cosmo_rug`: painted light blue by default, no collision.

Furniture models: the legacy Blockbench models as authored, with one block = 16 units and the front facing north. The Crates mod's `display.fixed` scale was the server's display size: scale 2 is the model's own size and scale 4 is twice it. Models are scaled to that size about the block's centre column and lifted to stand on the floor when they reach below it.
- Every piece keeps a `FurnitureBlockEntity` (`apeira:furniture`, `DecorBlockEntities.FURNITURE`, a `PaintBlockEntity`), and `client/FurnitureRenderer` draws the block's item in the `none` display context, turned by `ROTATION`. The block state is one variant for every rotation; the block model only gives the breaking particles.
- Small pieces: when the scaled model fits the -16..32 block model range, it is baked into `models/block/furniture/<name>.json`, which the item definition shows in the `none` context (`DecorBlockStateProvider#furniture`).
- Large pieces (130 of them): the item definition shows `models/item/furniture/<name>_placed.json` (the unscaled legacy model) in the `none` context, scaled and lifted as `Furniture.Large` says. The shape of a large piece stays inside its own block.
- Item models are the legacy item models, `<name>_inventory` where the Crates mod had one, in `models/item/furniture/`.
- Textures are in `textures/block/furniture/<crate folder>/`, `orfurniture/` and `cosmolib/`; the block atlas loads subfolders.
- Shapes come from the scaled model's cubes, clamped to the block and simplified as `parse_blockbench_hitboxes.py` does. A model with more than ten boxes falls back to 4-pixel cells.
- Seats are the pieces named chair, stool, bench, sofa, couch, seat, throne, armchair or loveseat. The seat height is the top of the highest cube over the block centre that is at most 14 pixels up.
- Not ported:
  - 99 Crates pieces have no model in the Crates mod (listed in the project's `legacy-port/gap-list.md`).
  - `office_ceiling_fan` hangs from a ceiling, which the furniture can't do yet.
  - `fishing_shack` uses a fish texture the mod lacks.
  - ORFurniture's `grand_father_clock` has no pendulum texture.
  - CosmoLib's `aged_flag` is an example piece, and `furniture_child` an internal multiblock placeholder.
  - The Crates mod's wall pieces are not ported.
- The old `oak_chair` stand-in is gone; the Crates mod's `saloon_chair`, the model it was made from, replaces it.

Datagen: `./gradlew :apeira-main:runDecorData` (the `decorData` run in apeira-main, `--mod apeira_decor`) writes to `apeira-decor/src/generated/resources/`, which is committed; CI runs it after `runData` and checks both folders. Each module's run only writes its own mod's providers, so a new decor block needs its block state, language, loot and tag entries in the decor providers, not the main ones.

Server pack: furniture models are in the pack's `assets/minecraft/items/firework_star.json` (`custom/furniture/...`), decorations and blocks in `paper.json`. Pack models for display entities are often offset (for example 8 pixels down); check that a model's cubes lie in 0-16 (backrests may reach higher) before using it as a block model.

CosmoLib unification: decor furniture and archae artifacts share CosmoLib's furniture and painting system, which apeira-archae implemented first. `ApeiraFurnitureBlock` (decor) is the one furniture base: eight-way `ROTATION`, `INVISIBLE` render shape, paint in a `PaintBlockEntity`, a block entity renderer drawing the block's item (`FurnitureRenderer`, `ArtifactRenderer`), seats through `SeatBlock`/`ApeiraSeatEntity`. Paint, placed or held, goes through the item pipeline (`apeira:paint` tint source, finish shaders); the old chunk-mesh path (`PaintBlockTint`, `FinishBlockModel`, `PaintFinishRenderer`) is gone. Placed decor furniture from before the change loses its turn (old `facing` states load as rotation 0) and its paint (small pieces' old `apeira:paint` block entities).

9. Painting (`apeira-decor`)
Ported from the legacy CosmoLib mod (`net.meh.cosmolib.paint`, `PaintingTableBlock`, `PaintingTableMenu`, `PaintingTableScreen`, `PaintbrushItem`; the GitHub repo `Meh-19/CosmoLib-NeoForge-1.21.X`, branch `menna-1`, matches the copy in `reference-code`). Code is under `com.apeira.decor.paint`, `.block`, `.item`, `.menu` and `.client`.

Paint: a 24-bit RGB value, either one of `PaintColor`'s nine colours times seven shades (CosmoLib's palette) or a `FinishType` (14 finishes stored under CosmoLib's reserved values: red and blue 255, green `(id - 1) * 2`). Items carry it in the `apeira:paint` data component (`DecorDataComponents.PAINT`, saved and synced; CosmoLib used a `PaintColor` int in `custom_data`). `Paint` reads and writes it, gives the tint (`Paint#tint`) and the tooltip line ("Painted Light Blue, Shade 3", "Gold Finish"), which the client adds to any painted item through `ItemTooltipEvent`.

Paintable blocks: implement `PaintableBlock` (an `EntityBlock` whose block entity is `PaintBlockEntity`, type `apeira:paint`, `DecorBlockEntities.PAINT`) and add the block to that type's valid blocks (it has none yet), or give it a block entity type of its own that extends `PaintBlockEntity`, as furniture and artifacts do. The block entity stores the paint as its `apeira:paint` component, so placing a painted item paints the block, pick-block copies it, and the loot table copies it back with `copy_components` (`DecorBlockLootSubProvider#dropSelfWithPaint`). Paint changes are sent with the vanilla block entity update packet. Placed paint is drawn as CosmoLib drew it, through the item pipeline: the block's renderer draws its item with the block's paint, and the item gets the `apeira:paint` item tint source (`PaintTintSource`, registered in `ApeiraDecorClient#registerItemTints`; datagen: `DecorBlockStateProvider#furniture`). A block family sharing one class implements `PaintableBlock` for all its blocks and answers `takesPaint()` per block: furniture takes paint when its model has `tintindex` faces, 171 of the 198 pieces. `FurnitureRenderer` and `ArtifactRenderer` copy the block entity's paint onto the item they draw.

`painting_table` (`PaintingTableBlock`, faces the player, front/side/top/bottom textures from CosmoLib, axe, drops itself; recipe: two white wool over four planks): opens `PaintingTableMenu` (`DecorMenus.PAINTING_TABLE`, screen `client/PaintingTableScreen`). Put a paintbrush or a paintable block's item in the input slot, pick a colour (3x3 grid) and shade (row below), or click the paint icon for the finishes (two pages of seven), and take one painted copy, which uses up one input. The screen sends its clicks as vanilla menu button clicks (`clickMenuButton`) and the selection comes back through data slots, so there are no custom payloads (CosmoLib had none either). GUI textures are `textures/gui/painting_table*.png`.

`paintbrush` (`PaintbrushItem`, 300 durability; recipe: feather, copper ingot, stick, stacked): gets its paint in the painting table. Right-clicking a paintable block paints it and costs one durability; sneak-right-clicking a painted block copies its paint onto the brush. It acts in `onItemUseFirst`, before the block's own right-click, so painting a chair does not sit on it. Model and textures are CosmoLib's Blockbench brush (`models/item/paintbrush.json`, `textures/item/paintbrush.png` and the animated `paintbrush_paint.png`, whose drip is `tintindex` 0).

Not ported, or changed:
- Finish effects are CosmoLib's shaders ported to render pipelines (`client/FinishRenderTypes`): `Paint#itemTint` gives an item a finish's paint value with alpha 254, and `mixin/ItemFeatureRendererMixin` (apeira-decor's `apeira_decor.mixins.json`) draws quads with that tint with the `apeira:pipeline/finish_item_cutout` or `_translucent` pipeline (with an OIT set). They use `shaders/core/finish_item.{vsh,fsh}` (vanilla's item shaders plus CosmoLib's finish code in `shaders/include/finish/`), which read the finish id from the vertex colour and sample `textures/misc/finish_atlas.png` as `FinishSampler`. Finishes show on every item path (GUI, hands, the ground, worn cosmetics, placed furniture and artifacts); `mixin/ItemModelResolverMixin` marks finished items as animated so the GUI redraws them. Enchanted (glint) items show the finish's representative colour (`Paint#tint`). The painting table's finish buttons are CosmoLib's finish previews: a stack whose `minecraft:item_model` is `apeira:finish_preview` (`items/finish_preview.json`, a flat paint button tinted by `apeira:paint`; no item is registered), painted with the finish and drawn with `GuiGraphicsExtractor#item`, so each shows its animated finish.
- Emissive pipelines (`client/EmissiveRenderTypes`): the alpha 254 rule (section 5) is `apeira_isEmissive` in `shaders/include/emissive.glsl`. `apeira:core/emissive_entity` and `apeira:core/emissive_item` are vanilla's entity and item shaders that keep the unlit vertex colour (`vertexTint`): an emissive texel skips the lightmap and face shading and is drawn at alpha 1. Pipelines `apeira:pipeline/emissive_entity_translucent` (and `_cull`) and `apeira:pipeline/emissive_item_translucent`, with OIT sets `apeira:emissive_entity`, `emissive_entity_cull` and `emissive_item`. GeckoLib renderers (crates, animated artifacts, the ruby deposit, the wraith, the starter balloon) use the entity types; `mixin/ItemFeatureRendererMixin` moves every quad drawn with vanilla's translucent item sheets to the emissive item type (`EmissiveRenderTypes#forItem`), so placed furniture, artifacts, cosmetics and held items follow the rule. The finish shaders apply it too. Painted GeckoLib bones (`*_tintable`) go through `client/TintedBones`, shared by animated artifacts and the starter balloon.
- The `cosmolib:paintable` block tag (empty in CosmoLib, and a block without a `PaintBlockEntity` has nowhere to keep paint). Paintable cosmetics are ported (section 10).
- Fixed from CosmoLib: the menu lost its input item when closed, shift-clicking the output gave a painted copy without using up the input, and `stillValid` was always true.

10. Cosmetics & Wardrobe (`apeira-decor` framework, `apeira-main` content)
Ported from CosmoLib (`net.meh.cosmolib.cosmetic`, its wardrobe screen and cosmetic layer) and the Crates mod (GitHub `Meh-19/Crates-NeoForge-1.21.1`; `CratesItems`, `models/cosmetics/`). Framework code is under `com.apeira.decor.cosmetic`, `.menu` and `.client`; the cosmetics themselves are `com.apeira.main.registry.MainCosmetics`.

`CosmeticItem`: a stack-of-one item with a `CosmeticSlot` (`HAT`, `BACK`, `HAND`), a `CosmeticRarity` (common, rare, epic, legendary, limited: the name colour and a badge glyph from the `apeira:cosmetic` bitmap font, `assets/apeira/font/cosmetic.json` and `textures/gui/lore_*.png`), whether it is paintable (paintable badge in the tooltip) and an optional default paint, set as the item's default `apeira:paint` component. The tooltip ends with the gold "<Theme> Crate Exclusive" line (`tooltip.apeira.exclusive.<crate>`); the paint line is hidden while a cosmetic keeps its default paint.

Painting: `Paint#canPaint` accepts paintable cosmetics, so the painting table paints them, and the paintbrush paints the paintable cosmetic in the other hand (right-click) or copies its paint (sneak-right-click). Painted faces are the model's `tintindex` 0 faces, through the `apeira:paint` item tint source.

Wardrobe: the `apeira:wardrobe` player attachment (`DecorAttachments.WARDROBE`, the `Wardrobe` record: one stack per slot), saved, kept on death and synced to every client tracking the player. The period key (`key.apeira.open_wardrobe`) sends `OpenWardrobePayload`; the server opens `WardrobeMenu` (`DecorMenus.WARDROBE`, screen `client/WardrobeScreen` on CosmoLib's `cosmetic_screen.png`, as `textures/gui/wardrobe.png`, with a turning player preview). The server menu's cosmetic slots are the attachment itself, so CosmoLib's trust in a client-sent stack is gone.

Render layer: `client/CosmeticLayer` is added to player and mannequin renderers of both skins (`EntityRenderersEvent.AddLayers`); `CosmeticLayer.MODIFIER` (a render state modifier) resolves the worn stacks into the avatar render state. The hat is drawn on the head as vanilla's head items, the back cosmetic on the body, the hand cosmetic in the off hand when it is empty, each with the item model's `head` (hat, back) or third-person hand display. Nothing is drawn for invisible players.

Content: 177 cosmetics in `MainCosmetics`, with the Crates mod's slots, rarities, paintability, default paints and crates. 127 have the mod's 3-D model (`models/item/cosmetic/<name>.json`, textures in `textures/item/`); their item definitions (`MainModelProvider#cosmetic`) show it only when worn, through the `apeira:worn_cosmetic` item model condition (`client/WornCosmetic`, true while `CosmeticLayer` resolves the wardrobe's models), and the rarity token (`item/<rarity>_<slot>_token`, apeira-decor's resources, shared with apeira-archae) everywhere else: inventories, hands, item frames, the ground. The other 50 had no model in the Crates mod and show only the token. Names and exclusive lines are in `MainLanguageProvider`.

Not ported, or changed:
- No Curios: CosmoLib kept its own wardrobe, and so does Apeira, as an attachment.
- Tool skins are not ported yet. The Crates mod's furniture is in apeira-decor (section 8).
- Finish effects are drawn on worn and held cosmetics as on other items (section 9).
- CosmoLib's per-cosmetic back offset config is replaced by `cosmetic/BackOffsets` (decor): a `BackOffset` per back cosmetic item (a move in the cosmetic's model pixels, a turn about x, y and z, a scale), which `CosmeticLayer` adds after the fixed back transform. Only apeira-dev sets them (section 13); exported values are not yet baked into anything.

11. Crates (`apeira-decor` framework, `apeira-main` content)
Ported from CosmoLib's `net.meh.cosmolib.crate` (`CrateEntity`, `CrateLootTable`, `CrateRarityWeights`, `CrateLuckAttachment`, `CrateCameraController`, `CrateHud`, `CrateItemLayer`, `CrateRenderer`) and the Crates mod's crate assets. Framework code is under `com.apeira.decor.crate`, `.network` and `.client.crate`; the crates are `com.apeira.main.registry.MainCrates`.

GeckoLib: apeira-decor depends on GeckoLib 5 (`com.geckolib:geckolib-neoforge-26.3`, version `geckolib_version` in `gradle.properties`, Cloudsmith maven) as an `api` dependency, and its mods.toml requires `geckolib`. GeckoLib's mixins make vanilla's render states implement its `GeoRenderState` at runtime; for compiling, apeira-decor passes a copy of GeckoLib's interface injections (`apeira-decor/geckolib_interface_injections.json`) to ModDevGradle's `interfaceInjectionData`. Update the copy when GeckoLib's changes. Files: `assets/<namespace>/geckolib/models/<path>.geo.json` and `geckolib/animations/<path>.animation.json`, both referred to as `<namespace>:<path>`.

Block: CosmoLib's crate was an entity placed by an item; Apeira's is a block, `CrateBlock` (`ROTATION_16`, kept even: crates face the placing player in 45 degree steps, as CosmoLib's did), with a `CrateBlockEntity` (`apeira:crate`, `DecorBlockEntities.CRATE`, valid for every `CrateBlock` of any module, collected from the block registry). The block renders `INVISIBLE`; its block model only gives breaking particles. A closed crate breaks and drops itself (loot table); while open it cannot be broken by players or explosions. Crate items stack to 16.

Opening (`CrateBlockEntity`, all server side, synced with the block entity update packet): right-click rolls three items and starts `OPENING` (76 ticks), then `LOOP`, where the opener crouches to collect or punches the crate to reroll (`REROLLING`, 60 ticks, 3 rerolls, `CrateEvents` handles the punch through `PlayerInteractEvent.LeftClickBlock`); after the last reroll the items are collected after 40 ticks. Collecting gives the items (dropping what does not fit), updates luck and plays `VANISHING` (16 ticks), then the block is removed. If the opener leaves (logout, other dimension, more than 8 blocks) the items drop and the crate vanishes. The opener gets Resistance V and `LivingIncomingDamageEvent` cancels any damage. The state, opener, rerolls and items are saved, so an opening survives a restart (CosmoLib reset to closed).

Loot (`CrateLoot`, loaded by `CrateLootManager` from `data/<namespace>/crate_loot/<crate>.json`, keyed by the crate's block id): lists of item ids for `common`, `rare`, `epic`, `legendary` and `limited`. Weights 60/25/10/4/1; the first item is always rare or better; an empty tier falls back to a lower one, then a higher one. Luck (`CrateLuck`, `apeira:crate_luck` player attachment, saved, kept on death, max 60) moves weight from common to rare (common never below 5): a legendary or limited resets it, three commons add 15, one rare and two commons add 8, two rares or more without an epic add 3. CosmoLib's `config/cosmolib/crate_rarity_weights.json` is replaced by constants in `CrateLoot`.

Client: `client/crate/CrateRenderer` (a `GeoBlockRenderer`) draws `geckolib/models/crate/<crate>.geo.json` with `textures/entity/crate/<crate>.png`, turned by `180 - yaw`; `CrateItemLayer` draws the rolled items on the model's `item1`-`item3` bones (scale 0.7, ground display) and, in `LOOP`, their names facing the camera. Animations are `geckolib/animations/crate/<crate>.animation.json` with clips `animation.<crate>.open`, `.open_loop`, `.reroll` and `.vanish` (CosmoLib asked for `animation.crate.*`, which the Crates mod's files do not have). `CrateOpenPayload` / `CrateUnlockPayload` lock and free the camera (`CrateCamera`: eases to the crate over 20 ticks, then keeps the player aimed at it; 25% slower, no hotbar scrolling); `CrateHud` shows CosmoLib's hints (`message.apeira.crate.*`).

Content: 15 crates in `MainCrates` (aether, animal, aquatic, atlantis, bathroom, beach, business, camping, construction, easter, fast food, festive, fun fair, garden, zodiac). Assets were copied from the Crates mod: geo models (with empty `item1`-`item3` bones added under `base`, which the animations move but the models lacked, and zodiac's `crate_base`/`crate_lid` renamed `base`/`lid` to match its animations), animations, entity textures, the crate item models (`models/item/<crate>.json`, texture moved to `textures/block/<crate>.png`). Loot is the Crates mod's `loot_tables/crates/<crate>.json`, with only the ported cosmetics and furniture kept. 13. Dev Tools (`apeira-dev`)
A dev-only module (mod id `apeira_dev`, `com.apeira.dev`) that depends on apeira-core and apeira-decor. apeira-main adds it as `localRuntime`, like apeira-archae, so `runClient`/`runServer` load it, but no content module depends on it and it is not shipped. It has its own `ApeiraRegistrar` and `ApeiraNetwork`; client entrypoint `client/ApeiraDevClient`. Its resources (item definition, `en_us.json`) are hand-made; it has no data run.

Furniture tuning (decor side): `FurnitureTuning` (decor `furniture/`) is a piece's shape boxes (pixels, facing north), scale and model offset (`offsetY` is `Furniture.Large#bottom`; X and Z move the model in its north-facing frame), rotation (45 degree steps added to the placing rotation), placements (`FurniturePlacement` bit mask: `FLOOR`, `WALL`, `CEILING`, and `DEFAULT`, floor placement always at the piece's own rotation instead of facing the player; untuned pieces may go on any face, `ANY_FACE`) and seat height. `FurnitureTunings` keeps them by block, one map shared by both logical sides. It is off unless a mod calls `FurnitureTunings#enable` from its constructor (apeira-dev does); then `FurnitureBlock` reports a dynamic shape (no cached shapes) and takes a tuned piece's shape, placement and seat height from it, and `FurnitureRenderer` draws it at the tuning's scale and offsets. Without apeira-dev furniture behaves exactly as before.

The furniture dev wand (`apeira:furniture_dev_wand`, `FurnitureDevWandItem`, in the Operator Utilities tab; a blaze rod model): right-click a decor furniture piece to bind the client's session to it (`client/DevSession`, from `PlayerInteractEvent.RightClickBlock`; the item's `onItemUseFirst` stops chairs seating you), sneak-right-click anything else to unbind. While held, `client/TuningHud` lists the piece's values (top left), Ctrl + scroll changes the selected one (1 pixel, Shift 0.25; scale 0.1, Shift 0.01), Alt + scroll selects another (`client/TuningParameter`), and K (`key.apeira.dev.furniture_editor`) opens `client/FurnitureEditorScreen`: typed values, box add/remove, placement toggles, reset to the catalogue, and Export. `client/TuningVisualizer` (a debug renderer, `RegisterDebugRenderersEvent`, drawn with vanilla's gizmos through blocks) shows the turned shape (white), the selected box (yellow), the seat (green) and the model's X/Y/Z axes and front.

Sync: edits go to the server as `FurnitureTuningPayload` (`apeira:furniture_tuning`, bidirectional; an empty tuning resets the piece). `TuningSync` accepts them only from creative operators (`Player#canUseGameMasterBlocks`), clamps them (`FurnitureTuning#sanitized`: boxes cut to the block and 24 pixels up, at most 64), sets them and sends them to every player; joining players get every tuning. Tunings live only in memory and are cleared when the server stops or the client leaves.

Export (`client/FurnitureExporter`, client side): writes the piece to `logs/apeira_furniture_export.json` in the game directory (`apeira-main/run/logs/` in dev), keyed by block id so the file collects every exported piece: boxes, scale, offset, model bottom, rotation, placements, seat height, and Java to paste: the shape as `Block.box` calls and the piece's `FurnitureCatalogue` line. The catalogue has no field yet for the X/Z offset, rotation or placements; the line lists them in a comment. The same Java is printed to the log.


Back cosmetics: while the wand is bound to no furniture piece and the player wears a back cosmetic, the HUD shows its `BackOffset` (`client/BackParameter`: offset X/Y/Z in the cosmetic's model pixels, pitch, yaw and roll in degrees, scale); Ctrl + scroll changes the selected value (1 pixel or 5 degrees, Shift 0.25 or 1; scale 0.1, Shift 0.01), Alt + scroll selects another, K exports it (`client/BackswagExporter`, `logs/apeira_backswag_export.json`, keyed by item id) and Shift + K resets it. Edits are `BackOffsetPayload` (`apeira:back_offset`, bidirectional), handled by `TuningSync` like furniture tunings (creative operators, sanitized, sent to all and to joining players, cleared when the server stops). Look at it in third person (F5). The HUD rows carry Ren's tool icons (`textures/gui/dev/tools.png`: add, move, turn, bin; duplicate, page, clipboard, undo) and the back mode Ren's axis gizmo (`axis_gizmo.png`: X red, Y green, Z blue).

Not covered yet: apeira-archae artifacts (they have their own shapes and placement, `ArtifactBlock`), hat and hand cosmetics' worn offsets, mob bounding boxes, and turning a piece without a seat into one (the seat height applies to seats only).

14. UI Capture (`apeira-uicapture`)
A client-only dev tool (mod id `apeira_uicapture`, `com.apeira.uicapture`) for copying server GUIs, such as Origin Realms' realm menus, 1:1. It depends on nothing but NeoForge, registers nothing and sends nothing, so its jar (`./gradlew :apeira-uicapture:jar`, `apeira-uicapture/build/libs/`) can go into a plain NeoForge 26.3 client to join any server; apeira-main also loads it in its runs (`localRuntime`). Its lang file is `assets/apeira_uicapture/lang/en_us.json`.

The "Capture UI Layout" key (`key.apeira.capture_ui`, F8, Miscellaneous) records the next frame of the open screen (any `Screen`, container or not; armed from `ScreenEvent.KeyPressed.Pre`, since key mappings are not clicked while a screen is open) or, with no screen open, of the HUD, then confirms with a toast and a chat line. While recording, the client mixins (`mixin/`, `apeira_uicapture.mixins.json`) log every texture blit, GUI sprite, atlas sprite, fill and item `GuiGraphicsExtractor` draws and every text `GuiRenderState#addText` receives, in draw order with their pose-transformed rectangles (`UiCapture`).

`UiCaptureWriter` writes `logs/apeira_ui_capture.json` in the game directory (the latest capture; `apeira-main/run/logs/` in dev) and keeps each one as `logs/apeira_ui_capture/captures/<time>_<title>.json`: GUI scale and size, loaded resource packs, the screen (class, title as text and component JSON), for container screens the image size, `leftPos`/`topPos`, label positions and every slot with its full item (all components: name, lore, item model, custom model data), the widget tree (class, bounds, message, state, the `Identifier`/`WidgetSprites` fields of its own classes), the drawn list, and for each font drawn with its definitions and, per codepoint, the bitmap (file, ascent, height, row, column) or space advance that holds it (`FontGlyphs`; servers draw custom GUIs as private-use glyphs in pack fonts). Every texture, sprite, font bitmap and font definition referred to is copied with its `.mcmeta` from the loaded packs, the server pack included, to `logs/apeira_ui_capture/assets/<namespace>/<path>` (`CapturedAssets`), and listed with its source pack. Text entries carry their width and height and are split into runs of one font and style, each with its colour (`color`, a name or `#RRGGBB`, and `rgb`), `shadow_color` and `formatting` (bold, italic, underlined, strikethrough, obfuscated); component fields (titles, widget messages) carry the same `runs`.

The "Deep Inspect UI" key (`key.apeira.inspect_ui`, F9) captures the open screen the same way and adds an `inspect` section, also written alone to `logs/apeira_ui_inspect.json`: the mouse position, the hovered slot with its item, the hovered widgets (parents first) with their messages, the text drawn under the mouse, and the tooltip (the text drawn inside the last `tooltip/*background` sprite). With no screen open it only says to open one.

Fabric build (`tools/uicapture-fabric/`): Origin Realms is played on Fabric 1.21.11, where a NeoForge 26.3 jar is skipped, so the same tool is also a standalone Fabric mod (Loom, Mojang mappings, Fabric API), outside Apeira's NeoForge build: `./gradlew -p tools/uicapture-fabric build` writes `tools/uicapture-fabric/build/libs/apeira_uicapture-fabric-<version>.jar`. Its capture code is a copy of the module's, adapted to 1.21.11's names (`GuiGraphics`, `GuiRenderState#submitText`, `GuiGraphics#renderItem`, accessors for the container's `leftPos`/`topPos`/image size and the private `Screen#renderables`); screens are armed and wrapped through Fabric's `ScreenKeyboardEvents`/`ScreenEvents`, the HUD through `mixin/GuiMixin` on `Gui#render`. Change both copies together.

Diagnostic tools (Fabric only): the sound inspector and the command logger live only in the 1.21.11 Fabric utility workspace (`tools/uicapture-fabric/`), client-side, never in the NeoForge modules: they read what an Origin Realms (or any) server sends a plain client, and nothing of them ships with Apeira. Both are Fabric client commands; they send nothing to the server except the command logger's probe completion requests.

Sound inspector (`SoundInspector`, a client command, since only the client has the packs' `sounds.json`; it was apeira-dev's): `/apeirasound <sound> [volume] [pitch]` (volume 0-10, pitch 0.5-2, both 1 by default) plays a sound event unattenuated and writes to chat and the log the variant it picked: file path, volume and pitch as played (the `sounds.json` entry's times the requested), attenuation distance (and its reach at that volume), whether it streams, the resource pack the file came from, its length and how long it plays at that pitch (read from the Ogg file: last page's granule position over the sample rate), and the subtitle key. `/apeirasound listen` toggles the sound log: every sound the client plays, the server's included (a `SoundEventListener`), is appended to `logs/apeira_sound_log.jsonl` with its milliseconds since the log started, event, file, pack, category, volume, pitch, attenuation, range, position and distance from the player, looping, delay, length and subtitle. Each logged sound is also one `[sound log]` line in the game log (event, file, volume, pitch, attenuation distance and type, subtitle key); `/apeirasound listen chat` turns the log on with those lines in chat too. Use them to time server sounds such as the Ruby ATM's `entity.atm_ruby.ambient`.

Command logger (`CommandLogger`): `/apeiracommands` writes the command tree the server sent (the commands the player may run) to `logs/apeira_command_capture.json`; `/apeiracommands <root>` also lists that command's usages in chat. Each root is marked `vanilla` (in a vanilla `Commands` dispatcher the client builds, `Commands.createValidationContext`, also under `minecraft:`), `client` (Fabric client commands) or `server`, with the plugin namespace it was also sent under (`essentials:pay`), its usages in `/apeiradev commands`' style (core's `CommandList`: `<argument>`, `a|b|c` endings, `-> target` redirects) and its full tree (literals, arguments with parser id and properties, custom suggestion ids such as `minecraft:ask_server`, executable, redirect). Plugin commands usually arrive as one greedy argument that asks the server, so their subcommands are not in the tree: `mixin/ClientSuggestionProviderMixin` (on `ClientSuggestionProvider#customSuggestion` and `#completeCustomSuggestions`) records the server's completion answers, the chat box's as one types and those of `/apeiracommands probe [root]`, which asks the server to complete every server command (or one), then each completion, up to 4 words deep (an answer that is mostly online player names follows only one), one request every 5 ticks to stay under Paper's tab-complete spam limit, at most 400, and writes the log when done. Probe requests use ids from `0x40000000`, and their answers are taken out before the chat box sees them. Answers are in the log's `server_suggestions` (input, start, completions with tooltips) and in `/apeiracommands <root>`'s chat lines (`/realm invite|kick|ban  (server)`); recordings are dropped when the connection changes. Probing sends only completion requests, as typing does.

Fabric client hooks (checked against the 1.21.11 Mojang-mapped jar): `ClientSuggestionProviderMixin` shadows `pendingSuggestionsId` and injects at HEAD of `customSuggestion(CommandContext)` (it pre-increments the id before sending `ServerboundCommandSuggestionPacket(int, String)`, hence `pendingSuggestionsId + 1`) and `completeCustomSuggestions(int, Suggestions)` (called on the client thread from `ClientPacketListener#handleCommandSuggestions`). A probe gives up after 40 ticks with no answer, because servers may send nothing when nothing completes. Commands the player sends to the server come from Fabric's `ClientSendMessageEvents.COMMAND` (no mixin; client commands are not included). They go to the game log as `[command logger] ran /...` and into the log's `ran_commands`, and are dropped when the connection changes. The sound inspector needs no mixin: `SoundEngine#play` calls every `SoundEventListener` (added through `SoundManager#addListener`) after the variant is resolved and before the silent-sound skip, so it sees every sound that resolves, muted ones included.

Armor stand recorder (`ArmorStandRecorder`, `ArmorStandExporter`, Fabric only, client commands): copies a server's multi-part armor stand animations (stands posed and re-equipped tick by tick) into a GeckoLib model and animation. Set the recording area first: `/apeiradev area pos1` and `/apeiradev area pos2` take the block under the crosshair (else the block one stands in), or `pos1 <x> <y> <z>`; `/apeiradev area` shows the area and how many armor stands are in it, `show`/`hide` toggle its outline (blue dust along the edges every 10 ticks, pos1 red, pos2 green; on by default) and `clear` forgets it. `/apeiradev record start [name]` records every tick (paused while the game is paused; the action bar shows the count and time), `/apeiradev record stop` exports, `cancel` drops it; leaving the world drops it too. Only armor stands whose position is inside the area are recorded (marker stands included; the `minecraft:marker` entity never reaches clients). Each tick keeps each stand's position, yaw, six poses, invisible/small/marker/arms/base plate flags and its six slots' items (id, `item_model`, custom model data, dye colour), and records events: `present` (in the area at the start), `spawn` (new entity, tickCount at most 2) or `enter`, `despawn` (gone from the level) or `exit` (still in the level, outside the area), `invisible`/`visible`, and `swap` (a slot's item changed, with `from` and `to`). Output in `logs/apeira_armor_stand_capture/<time>_<name>/`: `recording.json` (raw Java values per tick and the events), `<name>.geo.json` (a GeckoLib/Blockbench Bedrock model: one vanilla-shaped armor stand per recorded stand, `stand_<n>` with `_head`, `_body`, `_left_arm`, `_right_arm`, `_left_leg`, `_right_leg` pose bones whose cubes are in `<part>_model` bones, `_base_plate`, and empty `_head_item`, `_chest_item`, `_legs_item`, `_feet_item`, `_mainhand_item`, `_offhand_item` bones to attach item models to) and `<name>.animation.json` (`animation.<name>.recorded`: the stand bone's position relative to the area's bottom centre, yaw as `yRot - 180`, poses as recorded, Bedrock's mirrored x; visibility as scale: the stand 0 outside the area and 0.5 when small, `_model` bones 0 while invisible or armless, item bones 0 while their slot is empty, each change two keyframes 0.001 s apart; and `timeline` instructions per event as Molang Blockbench accepts, `v.event = '<type> <bone>';` or `v.event = 'swap stand_<n> <slot> <item|empty>';` (the item as id, item model and custom model data, quotes dropped; the full state JSON is in `recording.json`'s events), for a GeckoLib custom instruction handler to swap item models). For a multi-part model: stand where the whole animation is visible, put the corners around every part (the area is whole blocks, both corners included), start recording before triggering the server's animation, stop after it ends. The pose and yaw conventions follow GeckoLib's Bedrock reading and were not checked in game yet. `minecraft:interaction` entities (the invisible click hitboxes servers attach to such models) inside the area are recorded alongside the stands (`HitboxTrack`, `mixin/InteractionAccessor` for the private response flag): position, yaw, hitbox width and height and response each tick, with `present`/`spawn`/`enter`/`despawn`/`exit`, `resize`, `response`, `target_start`/`target_end` (the player's crosshair) and `attack`/`use` events (Fabric's `AttackEntityCallback`/`UseEntityCallback`, never cancelled; hand, response and the hit point relative to the hitbox's bottom centre). The server keeps who attacked or used an interaction to itself, so its answer shows only as the swaps and spawns in the ticks after a click. They export as `interaction_<n>` bones with a locator of that name and an `interaction_<n>_hitbox` cube of the first width and height (the animation moves them, hides them outside the area and scales the cube by size changes), and in `recording.json`'s `interactions` with their frames, offset from the area origin and from the nearest stand (also in that stand's own frame, x left, z forward). Every other non-player entity in the area is recorded too as a prop (`AreaEntities`, `PropTrack`): display entities (item, block and text: the item with its custom model data and item model, display context, block state, text and its JSON, line width, background, opacity, flags, billboard mode, and the transformation the server set, read through `mixin/DisplayAccessor`'s `createTransformation` rather than the interpolated render state: translation, left rotation, scale, right rotation), item frames and glow item frames (item, rotation 0-7, facing), dropped items and any other entity (type, position, name). Each tick keeps its position, yaw, pitch, state and transformation, with `present`/`spawn`/`enter`/`despawn`/`exit` and `change` events (the state keys that changed, `from` and `to`). They export as bones named after their item's model (the last part of the first model its definition resolves to, `badger_head`, else the item and its custom model data, `paper_cmd2319`; a repeated name gets `_2`, `_3` ...; props without an item keep `<kind>_<n>`: `text_display_0`, `block_display_0`, `entity_0`) with a locator; stands with equipment are named the same way after their first equipped slot's model, `<model>_stand`, else `stand_<n>`; display bones turn by yaw and pitch (a fixed billboard's turn, `rotationYXZ(-yaw, pitch, 0)`, once: the stands' `yRot - 180` is their own) and carry vanilla's matrix, translation * left rotation * scale * right rotation, in two bones, since a bone is translation * rotation * scale: `<bone>_transform` (translation, left rotation, scale) and its `<bone>_transform_right` child (right rotation), so it is exact for any scale; each bone's first recorded translation and rotation are its rest pose, baked into the geometry (`ArmorStandExporter#bake`): its pivot is its parent's pivot plus that translation (in the parent's unturned frame), the point vanilla turns and scales it about (the entity position, then the transformation's translation; item models are centred on it by their -8 pixel cube offset, block displays drawn from the block's corner), its cubes and locators move with it and its `rotation` is the rest rotation, so the static `.geo.json`/`.bbmodel` stands assembled, and every animation file keys positions and rotations only as the change from that rest pose (translation is never applied twice; GeckoLib and Blockbench add the keyed rotation to the rest one), scales absolute; `DisplayDiagnostics`' check reads the bones back through those pivots; `recording.json`'s `props` has every frame with the full state and transformation. `/apeiradev dumparea` lists the area's non-player entities in chat and the log: a count per entity type, then the items they show (stand equipment, item displays, frames, dropped items) counted by id, item model and custom model data, then each item display's transform chain (`DisplayDiagnostics`: entity id, item, custom model data, display context, translation, raw left and right quaternions, scale, each model's `display.<context>` transform, the bone values the export writes, and a check that draws the item's centre and top corner through vanilla's render chain and through the exported bones read back as GeckoLib does, with the delta in pixels); each export prints the same for every item display's first frame to chat and the log and writes it to `display_diagnostics.txt`. Loop detection (`AnimationSegments`): two ticks match when every stand, interaction and prop is in the area in both or neither and its position (0.01 blocks), angles (0.5 degrees), transformation (translation 0.01 blocks, scale 0.001, rotations the same turn within 1e-5), flags, items and state agree; the loop is the shortest period of at least 10 ticks, with motion, seen repeated in full at least once, starting as early as possible. Each export then also writes `<name>.transition.animation.json` (the ticks before the loop), `<name>.loop.animation.json` (one period, `loop: true`, its last frame its first) and `<name>.action.animation.json` (the ticks after the repeats end), clips `animation.<name>.transition|loop|action` over the same geometry and `root_rig`, and `segments.json` (tolerances, period, repeats, each clip's file and ticks); tracks absent from a clip are held at scale 0. A recording with no repeat whose first and last ticks match is one loop; one that never moves or has no repeat is not split, and `segments.json` says why. The full `<name>.animation.json` is always written. Every exported bone hangs from one top-level `root_rig` bone (pivot 0, the area's bottom centre; held at rest in the animation), so the whole rig moves or turns as one in Blockbench. Item displays' items are drawn (`ItemModels`, `ItemGeometry`, `TextureAtlas`, `Bbmodel`): each distinct item and display context a display shows is resolved from the loaded packs, the server pack included, as the client would: the item definition (`items/<item_model>.json`) evaluated for its custom model data and context (`model`, `range_dispatch`, `select`, `condition`, `composite`; other properties take their fallback, `on_false` or 0; `special` models are noted, not drawn), then each model's `parent` chain (textures and `display` merged, nearest `elements`), texture variables resolved to texture ids. It becomes a `<bone>_<item>` child of `<bone>_transform_right` (`<item>` its path and custom model data, `paper_cmd2319`) with one `<bone>_<item>_<model>` child per model, named after the model (composite definitions have several) holding its cubes (per-face UV; generated items as their layers' opaque pixels, one pixel deep) moved -8 pixels, turned by the display's half turn and scaled by that model's own `display.<context>` transform (translation, rotation in x, y, z order, scale, about the model's centre), which vanilla applies to the model before the entity's matrix: its translation and rotation are the model bone's rest pose, its scale is keyed; the animation scales each variant bone to 0 while the display shows another item or none, so item, custom model data and visibility swaps are keyframes. The textures (first animation frame) are packed into `<name>.png`, the geometry's one texture (the armor stand's at its top left, for the stands' box UV; missing textures magenta and black), and copied with the model and item definition files to `assets/<namespace>/...` in the export folder; `<name>.bbmodel` is the geometry as a Blockbench project (Bedrock format) with the atlas embedded, so it opens textured (import the animation file into it); `item_models.json` lists each variant's definition, models, parent chains, textures, display transform and notes, each texture's place in the atlas, and the copied files with their packs. Not drawn yet: stand equipment, item frames' and dropped items' items, block displays, face tints (dye, potions) and element `rescale`.

Datapack harvester (`DatapackExporter`, Fabric only, client commands): `/apeiradev export_datapack [namespace]` writes what the game has of the server's data as a datapack in `apeira_exports/datapack/` in the game directory (the instance folder; `run/` in dev), in 1.21+ folder names (`loot_table`, `recipe`, `advancement`, `structure`, `tags/block`, `worldgen/...`, `dimension_type`, `dimension`), with a `pack.mcmeta` of this version's data pack format and `export_report.json` (source, namespace, files, counts per category and per registry, what was skipped and what failed, also in the game log as `[export_datapack]`); chat gets the counts (loot tables, recipes, tag files, advancements, worldgen/registry entries, structures, files, failures) and one grey line per skipped part. Files are overwritten, never deleted. In singleplayer or a LAN world one hosts it reads the integrated server on its thread: loot tables, predicates and item modifiers (`reloadableRegistries`), recipes (`Recipe.CODEC`), advancements (`Advancement.CODEC`), every `RegistryDataLoader.WORLDGEN_REGISTRIES` and `DIMENSION_REGISTRIES` entry with its full codec, every registry's tags, and every structure template (`StructureTemplateManager#listTemplates`, `.nbt`). Joined to a remote server only what servers send clients exists: the `SYNCHRONIZED_REGISTRIES` entries with their network codecs (biomes have climate and effects but no features or spawns), every synchronized tag (flattened to element ids, as the client receives them), the advancements the player can see (parent, display, requirements; each criterion `minecraft:impossible`, as servers send only criterion names) and the recipe book's displays (`recipe_book_displays.json` beside `data/`, a report, not recipes: recipes stay on the server since 1.21.2); loot tables, recipes, worldgen features, dimensions and structure templates are listed as skipped. `/apeiradev export_structure <namespace:path>` saves the recording area (`/apeiradev area`) from the client's copy of the world as `data/<namespace>/structure/<path>.nbt` (`StructureTemplate#fillFromWorld`, entities included, blocks only if an entity cannot be saved client side), so a live server's builds can be taken for jigsaw pools or the NeoForge mod. A namespace argument exports only that namespace.

In 3-bit-per-channel colour buckets, the bucket with the most pixels is the skin tone; every other bucket at least 40 RGB units from it is a feature (eyes, mouth, markings, a mask), scored by its distance from the tone (over 441.7), saturation (plus 0.15), closeness of its lightness to 50% and the square root of its share, with pixels in the eye rows (face rows 3-4, skin y 11-12) counting three times (`feature`). The best feature's average colour is the accent, so the panel shows the colour of the player's eyes or the most distinct colour on their face. 16. Realms & Onboarding (`apeira-main`, `com.apeira.main.realm`, client in `client/realm`)
Each player's realm is its own dimension (`apeira:realm/<preset>_<hex>`), made while the server runs by `RealmLevels#create`: the overworld dimension type and noise settings, the preset's biome source and a seed of its own (NeoForge's `LevelStem` seed override; `landSeed` tries seeds until the border's centre and corners are inland), added to the server's level map through `mixin/MinecraftServerAccessor`, with a vanilla world border 300 blocks wide centred on 0, 0. `RealmPreset` is the five regions (lush, arid, cold, arctic, tropical): a multi-noise source of only its biomes, vanilla's and Xenon's, lowland biomes on eroded ground and mountain biomes below erosion -0.35, each group spread on a temperature/humidity circle. `RealmData` (overworld saved data `apeira:realms`) keeps the owned realms by player UUID and the pool.
Pool (`RealmPool`): the server keeps `READY_PER_PRESET` (1) realm of each preset made and generated ahead. On `ServerStartingEvent` every saved realm's level is recreated and missing pool slots are queued; each server tick (`ServerTickEvent.Post`, after the levels tick, so the level map is never changed while iterated) adds at most one queued dimension and moves the first ungenerated pool realm (one at a time) on by one 5x5-chunk batch (`addTicketAndLoadWithRadius` with a `player_loading` ticket, released when done), until the border area is generated; a last step loads the origin's chunks (`ORIGIN_RADIUS` 4, the flat-ground search's reach) and saves the spawn (top block at 0, 0) while they are loaded. Neither runs while a player is travelling to a realm or for 200 ticks after one arrives (`QUIET_TICKS`), so the chunk workers and server thread serve that player. `RealmPool#claim` hands the picked preset's pool realm to the player at once (a generated one first, or a new one if the pool is empty), queues a replacement, starts loading the realm's origin chunks in the background (`RealmPool#preload`, released on arrival, so the starter balloon's first build and the arrival find them loaded instead of loading 81 chunks at once on the server thread), and teleports the player there 60 ticks later. The onboarding screen loads its five region pictures (2276x1224) one a tick while it fades in from black, not on the frame each is first shown.
Onboarding (`client/realm/OnboardingScreen`, textures `textures/gui/onboarding/`, Origin Realms' cards and Ren's region pictures, positions measured at GUI scale 3): players without a realm get `OpenOnboardingPayload` on login, or from `/realm create`. The screen fades in from black over a second and cannot be closed (Esc or `onClose`) until a region is picked. The guide card ("Press F to continue"), then the region previews: 1-5 pick a region (cross-faded), tapping F goes to the next (tropical wraps to lush), holding F for 2 seconds fills the "Hold F to pick" bar with Origin Realms' `confirm_progress` texture (its progress font: rows 64, 32, ... 1 pixels wide, added up to the width), fades to black and sends `SelectRealmPresetPayload` (`apeira:select_realm_preset`); the server's `RealmCreatedPayload` shows "Realm Created", then "Traveling Home..." until the player arrives. `/realm home` teleports to the player's realm.
Starter balloon (`realm/balloon/`, registry `MainRealmBlocks`): the first time a realm is visited (`RealmPool#spawnOf`, once: `RealmAccess`'s `starter_built`), `StarterBalloon#build` finds flat ground for it (`StarterBalloon#flatSpot`: the column nearest 0, 0, within 48 blocks on each axis, whose 5x5 platform area has every top block, leaves ignored, at one height, dry and not under sea level; the top block at 0, 0 when there is none), clears the space over it and places Ren's platform structure there, `data/apeira/structure/starter_balloon_<wood>_platform.nbt` (5x5, 3 high: a beam-framed base, the floor with steps up on the north side, a fence ring round a 3x3 opening; oak for lush, acacia for arid, spruce for cold and arctic, jungle for tropical, `StarterBalloon#wood`), with `<wood>_beam` legs down to the ground from its corners, and the balloon on its floor; the realm's spawn becomes the block above the balloon unless the owner had set one. The platform is ordinary blocks and can be broken. The balloon is `starter_balloon` (`StarterBalloonBlock`, light 14, renders `INVISIBLE`; `StarterBalloonBlockEntity`, a decor `PaintBlockEntity` and GeckoLib block entity looping `RealmBalloonFloating`, drawn by `client/realm/StarterBalloonRenderer` from Ren's `geckolib/models/block/starter_balloon.geo.json` (`geometry.starter_balloon`, Ren's new model without the old platform cube; its basket is 3x3 blocks with the front on the north side, the envelope cube and its lower fringe (the 48x12x48 outer and inverted inner cubes, lavender at uv 48, 92 and 52, 104) moved into the `balloon_tint` bone; the block's `FACING` turns it through GeckoLib's block rotation), `textures/block/starter_balloon.png`, whose burner flame is alpha 254 and glows, animated at 2 ticks a frame without interpolation (Ren's `.mcmeta`); Ren's later export of the model is the same cubes with the envelope back in `group`, as Bedrock geometry keeps no cube names, so the shipped file keeps the envelope in `balloon_tint` (to tint more cubes, put them in a Blockbench group whose name ends with `_tint`); no item, no drops, strength -1, immovable).
Spawn facing (`RealmAccess#spawnFacing`, saved as `spawn_facing`, north by default): the first visit builds the balloon facing the arriving player's horizontal direction and the platform half a turn further (its structure turned about its centre column, `StarterBalloon#rotation` of the opposite direction, so Ren's north steps are behind the balloon); `/realm setspawn` with the balloon faces it towards the owner placing it (the opposite of the way they look), `/realm setspawn here` keeps the owner's way. 17. Rubies Economy & Ruby Deposit (`apeira-main`, `com.apeira.main.ruby`, client in `client/ruby`, registry `registry/MainRubies`)
